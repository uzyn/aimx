## 1. macOS: launchd agents vs daemons, SMAppService, Homebrew, signing/notarization, Gatekeeper, port 25, network prompts

### Takeaway
aimx's current architecture ports to macOS more directly than to Windows: a root LaunchDaemon can bind :25 (and even a non-root process can bind privileged ports on the wildcard address since Mojave), Unix domain sockets plus `getpeereid` give the same uid-based caller authz as SO_PEERCRED, and root daemons are exempt from Local Network privacy prompts. The real costs are distribution friction: a $99/yr Apple Developer Program membership is needed for Developer ID signing and notarization, bare CLI binaries cannot have notarization tickets stapled (a signed `.pkg` is Apple's suggested route), and Homebrew formulae with a `service` block are the lowest-friction install path for technical users.

### Cited Findings

**launchd: LaunchDaemons vs LaunchAgents**
- Apple describes daemons and agents as "essentially identical", differing in scope. Daemon plists go in `/Library/LaunchDaemons/` (third party), start at boot, and must be root-owned. Agent plists go in `/Library/LaunchAgents` or `~/Library/LaunchAgents`, start when a user logs in (via a per-user launchd), get SIGTERM at logout, and must be owned by that user. — [Apple: Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)
- Apple recommends against calling `setuid`/`setgid` in your own code and suggests the plist `UserName` / `UID` / `GroupName` / `GID` keys instead. launchd itself runs as root, which is why launchd socket activation can create low-numbered listening sockets for jobs (`Sockets` → `SockServiceName` accepts a numeric port such as "23"). Plists and executables must not be group- or world-writable. Jobs that exit within 10 seconds of launch may be treated as crashed. — [Apple: Creating Launch Daemons and Agents](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)

**SMAppService (macOS 13+)**
- Note: Apple's SMAppService page is JavaScript-rendered and could not be read, so the following is unverified against Apple's text. The fetch tool's fallback answer (from model background knowledge) said `SMAppService` (macOS 13 Ventura+) replaces `SMLoginItemSetEnabled` / `SMJobBless` and offers `.mainApp`, `.loginItem(identifier:)`, `.agent(plistName:)` (plist in `Contents/Library/LaunchAgents/`) and `.daemon(plistName:)` (plist in `Contents/Library/LaunchDaemons/`). Registration can land in a `.requiresApproval` state, which the user resolves in System Settings > General > Login Items & Extensions. — [Apple: SMAppService (page not rendered; see note)](https://developer.apple.com/documentation/servicemanagement/smappservice)

**Homebrew formula/tap + `brew services`**
- `brew services` drives `launchctl` on macOS and `systemctl` on Linux. Run without sudo, it installs user-level login services in `~/Library/LaunchAgents`. `sudo brew services` targets boot-level locations (`/Library/LaunchDaemons`). — [simplified.guide: Homebrew service start/stop](https://www.simplified.guide/homebrew/service-start-stop); [Homebrew FormulaWrapper API docs (boot_path vs user_path, keep_alive delegated to formula.service)](https://docs.brew.sh/rubydoc/Homebrew/Services/FormulaWrapper.html); [legacy brew-services gist](https://gist.github.com/766293)
- Ollama is a comparable case: the Homebrew install gives the CLI only (no menu-bar app), and launch-at-login comes from a launchd service named `homebrew.mxcl.ollama`. — [lmsa.app 2026 Ollama guide (secondary)](https://lmsa.app/blog/how-to-install-and-configure-ollama-on-windows-and-mac-complete-2026-guide/)
- Homebrew 5.0 (Nov 2025) deprecated `--no-quarantine` and said it would end support for casks that fail Gatekeeper checks on **September 1, 2026**. App developers distributing through casks must sign and notarize. I found no October 2026 source confirming the enforcement actually happened. — [AlternativeTo: Homebrew 5.0 news (Nov 2025)](https://alternativeto.net/news/2025/11/homebrew-5-0-brings-download-concurrency-by-default-linux-arm64-aarch64-support-and-more/); [Workbrew: Homebrew 5.0.0](https://workbrew.com/blog/homebrew-5-0-0)

**Code signing and notarization**
- Gatekeeper checks Developer ID signatures on software distributed outside the Mac App Store. Generating a Developer ID certificate requires being the Account Holder of an Apple Developer Program team. Notarization (`xcrun notarytool` for uploads, `xcrun stapler` to attach tickets) accepts ZIP, PKG and DMG. `altool` and Xcode 13 or earlier stopped being accepted on Nov 1, 2023. — [Apple: Developer ID](https://developer.apple.com/developer-id/)
- The Apple Developer Program costs **USD 99 per membership year**, and notarization requires the paid membership. Fee waivers go only to nonprofits, accredited schools and government entities, not individuals. (Secondary sources; I found no 2026 price change.) — [flaviocopes: free vs paid](https://flaviocopes.com/apple-developer-free-vs-paid/); [magora-systems, Aug 2026](https://magora-systems.com/apple-developer-fee/); [Apple forums: notarization refused for non-enrolled team](https://developer.apple.com/forums/thread/121113)

**Gatekeeper behavior: curl vs browser vs pkg**
- An Apple DTS engineer notes that most Unix-y tools, including `curl` and `scp`, don't quarantine their downloads. Gatekeeper usually only kicks in for quarantined files. So a `curl | sh` installer that fetches a binary does not trigger Gatekeeper, while a browser download does. — [Apple forums 666452](https://developer.apple.com/forums/thread/666452); [Apple forums 757647](https://developer.apple.com/forums/thread/757647)
- A bare single-file CLI binary cannot have a notarization ticket stapled to it. Apple's suggested distribution workaround is an installer package. If a quarantined tool is double-clicked in Finder, the Gatekeeper "document" check always fails however well it is signed. Run from Terminal, the normal check passes when the tool is signed and notarized. — [Apple forums 757647](https://developer.apple.com/forums/thread/757647); [Apple forums 689337](https://developer.apple.com/forums/thread/689337)
- macOS Sequoia (2024) removed the Control-click override for software that isn't signed correctly or notarized. Users must instead go to System Settings > Privacy & Security > "Open Anyway". Reports conflict on whether Control-click works again after the first approval. — [The Hacker News, Aug 2024 (quotes Apple)](https://thehackernews.com/2024/08/apples-new-macos-sequoia-tightens.html); [Macworld](https://www.macworld.com/article/2457844/what-to-do-when-you-cant-open-an-app-you-just-installed-in-macos-sequoia.html); [Michael Tsai blog (Jason Snell beta observation)](https://mjtsai.com/blog/?p=43993)

**Binding port 25 without root**
- Since macOS Mojave, non-root processes can bind privileged ports (<1024) on the wildcard address (INADDR_ANY). Apple DTS (Quinn, Feb 2021): "iOS never had this restriction and we've now lifted it on macOS", "an intentional change and we don't plan to change it back". Apple engineers also said it was never officially documented. — [Apple Developer Forums thread 674179](https://developer.apple.com/forums/thread/674179)
- Caveat: binding a privileged port to a *specific* address (for example, 192.168.1.30 or 127.0.0.1 alone) still returns EACCES for non-root. Quinn answered "No" when asked whether this would be addressed. A user report on the macOS 26.0 beta (Jul 2025) says the behavior is unchanged. — [Apple Developer Forums thread 674179](https://developer.apple.com/forums/thread/674179); [Caddy community](https://caddy.community/t/how-is-caddy-able-to-bind-to-port-80-and-443-on-macos-without-root/15293)

**Local Network privacy and firewall prompts**
- Apple DTS: programs running as root, including launchd daemons and their child processes, are automatically granted local network access. A macOS 15.0 bug (FB14812974) kept the exemption from covering DNS operations; it was fixed in 15.1. Launch *agents* must ask for permission. — [Apple forums 767391](https://developer.apple.com/forums/thread/767391); [Apple forums 759955](https://developer.apple.com/forums/thread/759955); [Eclectic Light, Jan 2026](https://eclecticlight.co/2026/01/14/how-local-network-privacy-could-affect-you/)
- Some developers report the prompt still appearing for root daemons in edge cases (one via a CUPS call). DTS attributed some of these to beta bugs. — [Apple forums 763484](https://developer.apple.com/forums/thread/763484); [Apple forums 778457](https://developer.apple.com/forums/thread/778457)

**Peer credentials on macOS UDS (relevant to aimx's SO_PEERCRED authz)**
- Tokio's `UnixStream::peer_cred()` on macOS/iOS uses `getpeereid` for uid/gid and `LOCAL_PEEREPID` for pid. Linux uses SO_PEERCRED, FreeBSD LOCAL_PEERCRED, NetBSD LOCAL_PEEREID. — [tokio source: net/unix/ucred.rs](https://github.com/tokio-rs/tokio/blob/master/tokio/src/net/unix/ucred.rs)

**Comparable macOS designs**
- Tailscale ships three macOS variants: the Standalone app (recommended, from Tailscale's package server), the Mac App Store app, and the open-source CLI-only `tailscaled`, which is the only one with the separate `tailscale`/`tailscaled` split and runs as a launchd service. — [Tailscale: three ways to run on macOS (search result)](https://tailscale.com/docs/concepts/macos-variants); [Tailscale: tailscaled reference (search result)](https://tailscale.com/docs/reference/tailscaled)
- `cloudflared service install` run as root installs a system LaunchDaemon that starts at boot. Run as a regular user, it installs a per-user LaunchAgent that runs only after login. (Older source commit.) — [cloudflared mirror commit TUN-5881](https://git.nixnet.services/curben/cloudflared-mirror/commit/1b511b2d259db8e2c220313d34b74d443189b383)
- Stalwart's `sudo sh install.sh` creates a service account, installs under Unix paths, writes a systemd, SysV or launchd unit depending on OS, enables it at boot and starts it. On macOS it is restarted with `sudo launchctl kickstart -k stalwart.mail`. — [Stalwart: Linux/macOS install](https://stalw.art/docs/install/platform/linux); [Stalwart 0.15 docs](https://www.stalw.art/docs/0.15/install/platform/linux/)

### Inferences
- **Lowest-effort macOS path (server, Mac mini):** reuse the Linux model. Ship a root LaunchDaemon plist in `/Library/LaunchDaemons/` (written by `aimx setup`, mirroring today's systemd/OpenRC writer), keep the UDS (move it from `/run/aimx/` to something like `/var/run/aimx/`), and keep uid-based authz via tokio `peer_cred()`. The setuid-to-mailbox-owner model works the same on macOS, since a root daemon can `setuid`. The only Linux-specific piece that breaks is `systemd-run` hook sandboxing (see section 5).
- **Desktop per-user path:** a LaunchAgent in `~/Library/LaunchAgents` running as the user can still bind :25 on 0.0.0.0 (Mojave+ behavior), but not on a specific IP. It would hit Local Network privacy prompts only for LAN destinations. Outbound SMTP to internet MX hosts is not "local network", so this is probably a non-issue, but that is unverified.
- **Distribution choice:** (a) a Homebrew tap formula with a `service do` block gives `brew services start aimx` (user LaunchAgent) or `sudo brew services start aimx` (LaunchDaemon) for free, with no Apple fee required for formulae. (b) A `curl | sh` installer avoids quarantine entirely, so it also avoids Gatekeeper. (c) A Developer ID-signed and notarized `.pkg` is the only "double-click from browser" path that is clean under Sequoia, and it costs $99/yr. SMAppService is only relevant if aimx ships a `.app` bundle (for example, a menu-bar app). For a CLI plus daemon it adds an app-bundle requirement and is overkill.
- The Homebrew Sept 2026 Gatekeeper rule applies to *casks* (app bundles). Formulae appear unaffected, which favors a formula for aimx (inference; not confirmed in sources).

## 2. Windows: services, installers, signing/SmartScreen, AF_UNIX vs named pipes, firewall

### Takeaway
Windows is the biggest lift. There is no `setuid`, no SO_PEERCRED-equivalent uid on AF_UNIX (only a spoofable PID ioctl), and tokio does not support AF_UNIX on Windows (issue open since 2020, "no plans"). The proven pattern, which Tailscale uses, is a Windows Service plus a named pipe with an explicit SDDL. The server identifies callers by impersonating the client token (`ImpersonateNamedPipeClient`) and reading its SID, not by PID. Signing is now cheap if you qualify: Azure Artifact Signing (formerly Trusted Signing) costs $9.99/month, but individuals are limited to the US and Canada. EV certificates no longer bypass SmartScreen, so new builds start with zero reputation regardless.

### Cited Findings

**Running as a Windows Service**
- The `windows-service` crate (0.8.1) provides service implementation and management. `define_windows_service!` generates the low-level entry function, and `service_dispatcher::start` blocks `main` until the service stops. Control events such as stop and pause come through a control handler. — [docs.rs windows-service (search result)](https://docs.rs/windows-service); [docs.rs windows-service 0.8.1 source (search result)](https://docs.rs/crate/windows-service/latest/source/src/lib.rs)
- Shims are common in comparable projects. Stalwart's official Windows route is to run `stalwart-mail.exe --init` and then `nssm install Stalwart_Mail` (or AlwaysUp), with no Windows install script. Syncthing's docs wrap it with NSSM and start it with `sc start syncthing`. — [Stalwart: Windows install](https://stalw.art/docs/install/platform/windows); [Syncthing: autostart](https://docs.syncthing.net/users/autostart)
- Native-service examples: Tailscale runs `tailscaled` as a Windows service named "Tailscale". `ngrok service install --config <file>` registers a native Windows service (logs to the Windows Event Log) and, on macOS, a launchd plist; it usually needs admin/sudo, and the exe and config must stay in place after install. — [Tailscale tailscaled reference (search result)](https://tailscale.com/docs/reference/tailscaled); [ngrok: installing as a service](https://ngrok.com/docs/secure-tunnels/ngrok-agent/installing-as-a-service)
- Per-user background app alternative: Ollama's Windows installer needs no Administrator rights. It installs under the user's home directory (relocatable with `/DIR`) and runs in the background as a native tray app, with the API at `http://localhost:11434`. A standalone `ollama-windows-amd64.zip` exists for people who want to run `ollama serve` as a system service via NSSM. — [Ollama docs: windows.mdx](https://github.com/ollama/ollama/blob/main/docs/windows.mdx)

**Installers: MSI, winget, Scoop, MSIX**
- cargo-dist's MSI installer uses WiX v3 via cargo-wix ("WiX v4 isn't yet supported"). It installs to `%ProgramFiles%\{app}`, optionally adds to PATH, keeps a stable `upgrade-guid`, shows in Add/Remove Programs, and must be built on Windows (GitHub CI has WiX v3 preinstalled). The docs say it has "a few rough edges" and don't mention installing Windows services. — [cargo-dist book: msi.md](https://github.com/axodotdev/cargo-dist/blob/main/book/src/installers/msi.md)
- winget manifests are multi-file YAML under `manifests/<letter>/<publisher>/<app>/<version>/`. The installer manifest carries architecture, installer type, URL, SHA256 and, for MSIs, the ProductCode; one manifest per PR. The older winget-pkgs README said only MSIX, MSI or .exe installers were accepted (no zip/portable). Newer winget-cli docs list `zip` and `portable` among installer types, so current policy is unconfirmed. — [Microsoft Learn: winget manifest (search result)](https://learn.microsoft.com/windows/package-manager/package/manifest); [winget-cli manifests concept (mirror)](https://www.mintlify.com/microsoft/winget-cli/concepts/manifests); [winget-pkgs issue 650](https://github.com/microsoft/winget-pkgs/issues/650)
- A third-party index lists axodotdev's own `dist` on winget as a ZIP install (`axodotdev.dist` 0.31.0), which suggests portable/zip packages are accepted in practice. — [wingetly: axodotdev/dist](https://wingetly.io/apps/axodotdev/dist)

**Code signing: Authenticode, EV vs OV, Azure Artifact Signing**
- Azure Artifact Signing (renamed from Trusted Signing) costs **$9.99/month (Basic, 5,000 signatures)** or **$99.99/month (Premium, 100,000 signatures)**, with overage beyond quota. Billing starts when the account is created. — [Azure pricing page (search result)](https://azure.microsoft.com/cs-cz/pricing/details/artifact-signing/); [my-ssl.com comparison](https://my-ssl.com/learn/azure-trusted-signing-vs-code-signing-certificate); [devclass, Jan 14 2026](https://www.devclass.com/security/2026/01/14/code-signing-windows-apps-may-be-easier-and-more-secure-with-new-azure-artifact-service/4079554)
- Eligibility: public-trust certificates are available to **organizations** in the US, Canada, EU, UK, Australia, New Zealand, Japan, South Korea, Singapore, Switzerland, Norway and Israel. **Individual** developers must be in the US or Canada. Microsoft's guide says individuals elsewhere should buy OV certificates from DigiCert, Sectigo or GlobalSign. — [Microsoft Learn: Artifact Signing quickstart (search result)](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart); [Microsoft Learn: code signing options (search result)](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options); [Azure/artifact-signing-action issue 42](https://github.com/Azure/artifact-signing-action/issues/42)
- Conflicts: a Microsoft Q&A thread (about early 2026) reported individual onboarding paused, and a country-unavailable complaint exists. A 2026 blog says Japanese entities could not use the service as of July 2026, which contradicts Japan being on Microsoft's org list. — [MS Q&A: Artifact Signing](https://learn.microsoft.com/en-ie/answers/questions/6020935/artifact-signing); [MS Q&A: country not available](https://learn.microsoft.com/en-nz/answers/questions/5810735/cant-create-a-new-trusted-signing-individual-ident); [codenote.net 2026](https://codenote.net/en/posts/windows-code-signing-ci-cost-per-signing-volume-2026/)
- cargo-dist 0.33.0 (released 2026-09-10) added Azure Artifact Signing for Windows binaries and installers (x86_64 Windows only). — [cargo-dist releases](https://github.com/axodotdev/cargo-dist/releases)
- SmartScreen: Microsoft's docs say EV certificates no longer bypass SmartScreen, and paying for EV solely to avoid warnings "is no longer justified". **IPC: AF_UNIX on Windows**
- Windows added AF_UNIX in Windows 10 build 17063, with limitations compared to POSIX: notably no SCM_RIGHTS and very limited credential passing. — [freedesktop D-Bus MR 249](https://gitlab.freedesktop.org/dbus/dbus/-/merge_requests/249)
- Windows exposes `SIO_AF_UNIX_GETPEERPID`, which returns the peer PID only. It is "roughly equivalent" to SO_PEERCRED but carries no uid/SID. — [Wine bug 60201](https://list.winehq.org/hyperkitty/list/wine-bugs@list.winehq.org/thread/D5XYEW4MKQX2RCOLQVOMH6I2HBCXGDGY/); [mingw-w64 afunix.h](https://mingw.googlesource.com/mingw-w64/+/refs/heads/v14.x/mingw-w64-headers/include/afunix.h)
- **Tokio does not support AF_UNIX on Windows.** Issue #2201 (opened Jan 2020) is still open. Maintainer Darksonn (Oct 2021): "We don't currently have any plans to work on this feature." It is blocked on mio, whose PRs #1610 and #1667 were not merged. Tokio does support Windows named pipes. — [tokio issue #2201](https://github.com/tokio-rs/tokio/issues/2201)
- Rust std has a PR adding UDS types under `std::os::windows::net`, gated behind the unstable `windows_unix_domain_sockets` feature (tracking #56533). — [rust-lang/rust PR 147335](https://github.com/rust-lang/rust/pull/147335)
- Ecosystem workaround: zbus relies on the `uds_windows` crate. — [zbus MR 468](https://gitlab.freedesktop.org/dbus/zbus/-/merge_requests/468)

**IPC: named pipes with per-caller identity**
- `GetNamedPipeClientProcessId` returns the client PID. `ImpersonateNamedPipeClient` makes the server thread adopt the security context of the last message read from the pipe (server end only), and `RevertToSelf` ends impersonation. — [MicrosoftDocs win32: pipe functions](https://github.com/MicrosoftDocs/win32/blob/docs/desktop-src/ipc/pipe-functions.md); [ImpersonateNamedPipeClient reference](https://msdn.microsoft.com/en-us/library/aa378618)
- James Forshaw (Google Project Zero, 2019) showed the named-pipe client PID can be spoofed and should not be used for enforcement. Authorize on the impersonated token/SID instead. — [Project Zero: Windows Exploitation Tricks: Spoofing Named Pipe Client PID](https://projectzero.google/2019/09/windows-exploitation-tricks-spoofing.html)
- Tailscale's production pattern (`safesocket/pipe_windows.go`): the LocalAPI listens by default under `\\.\pipe\protectedprefix\administrators\`, a prefix where creating a pipe requires admin, which prevents squatting. The SDDL `D:P(A;;GWGR;;;BU)(A;;GWGR;;;SY)` grants read/write to Built-in Users and SYSTEM. Clients dial with `PipeImpLevelIdentification` so tailscaled can inspect the caller's token. The server gets identity via `ImpersonateNamedPipeClient` → open thread token → revert, and also exposes `GetNamedPipeClientProcessId`. A per-user variant uses `O:<sid>D:P(A;;GWGR;;;<sid>)`, and clients verify that owner and DACL are exclusive to the current user. — [tailscale/safesocket/pipe_windows.go](https://github.com/tailscale/tailscale/blob/main/safesocket/pipe_windows.go)
- Historical lesson: Tailscale's Windows LocalAPI was once bound to a local TCP socket (`localhost:41112`), which led to CVE-2022-41924 (fixed in v1.32.3). — [INCIBE: CVE-2022-41924](https://www.incibe.es/index.php/en/incibe-cert/early-warning/vulnerabilities/cve-2022-41924); [Tailscale forum: Using localapi](https://forum.tailscale.com/t/using-localapi/736)

**Firewall and port 25**
- Windows Defender Firewall's `inboundusernotification` setting controls whether the user is notified when a program starts listening for inbound connections. Program-scoped allow rules are distinct from port rules (`netsh advfirewall firewall add rule ... dir=in ... action=allow`). — [Microsoft Learn: netsh advfirewall (search result)](https://learn.microsoft.com/en-in/WINDOWS-SERVER/administration/windows-commands/netsh-advfirewall); [computingforgeeks: open a port in Windows Server firewall](https://computingforgeeks.com/how-to-open-a-port-in-windows-server-firewall/)
- Whether modern Windows restricts binding ports <1024 to privileged processes is contested. NT-era sources and an undated Broadcom KB say any user can bind any port (including 25). An old Microsoft KB 174904 calls 0–1023 "privileged". — [Broadcom KB 159944](https://knowledge.broadcom.com/external/article/159944/unable-to-use-port-25-within-linux.html); [insecure.org NT port binding](https://insecure.org/sploits/NT.port-binding-vulnerability.html); [MS Q&A citing KB 174904](https://learn.microsoft.com/en-us/answers/a/3154028)

### Inferences
- **Recommended Windows architecture:** an `aimx serve` Windows Service (via the `windows-service` crate, LocalSystem or a virtual service account) listening on a named pipe under the `protectedprefix\Administrators` namespace with an SDDL modeled on Tailscale's. Authz would key on the caller token's user SID instead of the uid, so the `auth::authorize` predicate needs a platform-neutral `Principal` type (uid on Unix, SID on Windows). PID-based checks should be avoided.
- **Hooks without setuid:** running a hook "as the mailbox owner" on Windows requires obtaining that user's token. Either (a) duplicate the impersonated token of the connecting client at hook-create time, which doesn't persist across reboots, or (b) store hooks to run under a restricted token derived from the service, or (c) run hooks only in a per-user daemon. Options (a) and (b) are substantially more complex than Unix `setuid` (inference).
- **Per-user desktop mode** (Ollama-style: no admin, user-scope install, autostart at login) sidesteps multi-user authz entirely. The pipe is owned by the user's SID only (Tailscale's `listenCurrentUser` pattern), and the firewall prompt appears on first listen unless an installer adds a program rule, which needs admin.
- **Installer path:** start with a zip (portable) on winget/Scoop plus a `powershell -c "irm ... | iex"` installer from cargo-dist, signed with Artifact Signing if the publisher qualifies. Add an MSI later if service install is needed: cargo-dist's MSI does not install services, so `aimx setup` would register the service itself, as `ngrok service install` does.
- **Effort estimate (inference):** Windows support is likely the largest single workstream. It needs a new IPC transport, a new authz principal model, a service wrapper, a new hook-execution model, path and permission (ACL) handling for storage, and CI signing.

## 3. Linux: existing systemd/OpenRC, user-level systemd units, .deb/.rpm, Homebrew on Linux, install.sh

### Takeaway
Linux is already the strongest platform for aimx. The incremental options are (1) .deb/.rpm packages that ship the existing systemd unit (cargo-deb has first-class `systemd-units` support), (2) Homebrew on Linux, where `brew services` maps to systemctl, and (3) an unprivileged per-user mode via systemd user units plus `loginctl enable-linger` so the daemon survives logout and starts at boot. A non-root daemon still cannot bind :25 by default without extra privilege configuration.

### Cited Findings
- Enabling linger (`sudo loginctl enable-linger <user>`) makes systemd spawn that user's manager at boot and keep it after logout, so user services with `WantedBy=default.target` run without an active login. Without linger, user units stop at logout. — [etbe: Systemd Linger, Jul 2026](https://etbe.coker.com.au/2026/07/24/systemd-linger/); [oneuptime: enable-linger for rootless Podman, Mar 2026](https://oneuptime.com/blog/post/2026-03-17-use-loginctl-enable-linger-rootless-podman/view); [Red Hat Learning community](https://learn.redhat.com/t5/Platform-Linux/User-Manager/m-p/57352)
- Syncthing offers both a system template unit `syncthing@<user>` (runs at boot without a session, suited to servers) and a user unit `syncthing.service` (`--user`, starts at login). — [Arch Wiki: Syncthing](https://wiki.archlinux.org/title/Syncthing); [Arch packaging commit](https://gitlab.archlinux.org/archlinux/packaging/packages/syncthing/-/commit/49080eef38aed5ada968f8df5b544592ae0f891d)
- cargo-deb supports `[package.metadata.deb.systemd-units]` for automated installation of systemd units, manual maintainer scripts, cross-compilation from any Unix-like host (including macOS), and automatic conffile treatment for `/etc`. — [cargo-deb README](https://github.com/kornelski/cargo-deb)
- `brew services` uses systemctl on Linux. — [simplified.guide: Homebrew services](https://www.simplified.guide/homebrew/service-start-stop)
- Stalwart's single `install.sh` handles systemd, SysV init and launchd from one script, an example of a cross-Unix installer for a mail server. — [Stalwart: Linux/macOS install](https://stalw.art/docs/install/platform/linux)
- `service-manager` supports user-level services for systemd and launchd via `ServiceLevel::User`, as well as OpenRC. — [service-manager-rs README](https://github.com/chipsenkbeil/service-manager-rs)

### Inferences
- For per-user Linux installs, the daemon needs a way to bind :25 as non-root. Options include `setcap cap_net_bind_service` on the binary, `AmbientCapabilities=` in a system unit with `User=`, the sysctl `net.ipv4.ip_unprivileged_port_start`, or listening on a high port with a redirect. None of these was verified in this research (background knowledge only), and most need root once at install time.
- A user-level install would lose the multi-tenant model (per-mailbox owner uid, setuid hooks). It is effectively single-owner mode, which matches the desktop use case.
- cargo-generate-rpm was not researched in depth. For parity with .deb it is the natural choice (background knowledge), but this is unverified.

### Gaps
- cargo-generate-rpm feature set (systemd scriptlets) not verified.
- Whether cargo-deb's systemd support covers *user* units and auto-enable/start was not visible in the README (it lives in a separate systemd.md).
- Non-root :25 binding mechanisms on Linux not sourced.

## 4. Cross-platform Rust crates and release tooling: service-manager, interprocess, directories/dirs, keyring, cargo-dist (dist)

### Takeaway
The building blocks exist but are uneven. `service-manager` (0.10) abstracts launchd, systemd, OpenRC, sc.exe and WinSW install/start/stop, with differing restart semantics per backend. `interprocess` (2.4.3) unifies UDS and named pipes with tokio support, but I could not confirm it exposes peer credentials, so aimx would still need platform-specific authz code. `directories` moved from GitHub to Codeberg (Feb 2025) and covers user dirs only. `keyring` split into `keyring-core` plus per-store crates. cargo-dist is actively maintained (0.33.0, Sept 2026) and covers shell, PowerShell, Homebrew, npm and MSI installers, an experimental updater, and now Azure Artifact Signing.

### Cited Findings
- **service-manager:** a `ServiceManager` trait with `install`/`uninstall`/`start`/`stop` and `ServiceManager::native()` platform detection. Backends: sc.exe and WinSW (Windows), launchd (macOS), systemd and OpenRC (Linux), rc.d (FreeBSD). User-level support is documented for systemd and launchd. Restart policies vary: launchd only distinguishes never vs always/on-failure (KeepAlive bool), and OpenRC, rc.d and sc.exe have limited or no restart support. README pins `service-manager = "0.10"`. About 246 stars and 11 open issues; last-commit date not visible. — [service-manager-rs](https://github.com/chipsenkbeil/service-manager-rs)
- **interprocess:** version 2.4.3. Its flagship "local sockets" are described as "a much more appropriate alternative to localhost TCP sockets", using UDS on Unix and named pipes on Windows. Tokio is the only supported async runtime (`tokio` feature, off by default). Windows, Linux and macOS have full CI. The page does not mention peer credentials or client PID/uid. The author states they will not cooperate with contributors using LLM coding assistants or users seeking support for LLM-based projects. — [kotauskas/interprocess](https://github.com/kotauskas/interprocess)
- **directories:** `ProjectDirs` maps to XDG dirs on Linux, `~/Library/Application Support/<reverse-domain>` on macOS, and roaming/local AppData on Windows. The latest changelog entry is v6 (dirs-sys 0.5.0). — [dirs-dev/directories-rs](https://github.com/dirs-dev/directories-rs)
- **keyring:** a cross-platform wrapper for native secure stores (Mac, Windows, *nix). The library/API moved into `keyring-core`, and credential stores now live in separate crates. Maintained by Dan Brotsky. — [open-source-cooperative/keyring-rs](https://github.com/open-source-cooperative/keyring-rs)
- **cargo-dist (dist):** releases 0.30.3 (2025-12-14, fixes macOS codesigning config and sudo shell-installer permissions), 0.31.0 (2026-02-23, "simple" static-mirror hosting), 0.32.0 (2026-05-21), and 0.33.0 (2026-09-10, Azure Artifact Signing). - The updater (axoupdater, `install-updater = true`) is **experimental**. It is bundled only with the shell and PowerShell installers as `<app>-update`, or used as a library. Homebrew and npm users update via their package manager. ### Inferences
- Because aimx's install already happens in `aimx setup` (writing unit files), `service-manager` could replace hand-written systemd/OpenRC writers and add launchd and sc.exe. Its restart-policy gaps on launchd and sc.exe, and the README's advice to use backend-specific managers for advanced options, suggest aimx may still want custom plist and service code for production quality.

Plausibly simpler: tokio `UnixListener` on Unix plus tokio `named_pipe` on Windows behind an aimx-internal trait.
- The interprocess maintainer's stated anti-LLM-user stance could be a support-risk consideration for an AI-agent product.
- cargo-dist would cover aimx's release matrix (Linux/macOS/Windows binaries, curl/irm installers, Homebrew tap, MSI, signing). It does not generate .deb/.rpm or a macOS .pkg per the installers directory listing, so those need cargo-deb, cargo-generate-rpm and pkgbuild/productsign separately.

## 5. Hook sandboxing per OS

### Takeaway
There is no portable sandbox. Linux has the richest unprivileged options (Landlock since 5.13, network rules since 6.7, plus systemd-run/bubblewrap). macOS's `sandbox-exec` (Seatbelt) has been deprecated since about 2016 but still works on Sequoia and is what Codex CLI, Claude Code, Bazel and Chromium reportedly use. Windows is hard: OpenAI's Codex team built a custom restricted-token design after rejecting AppContainer, and still labels it experimental.

### Cited Findings
- **macOS sandbox-exec:** deprecated (since macOS Sierra, 2016) but "still what everyone uses". Reported users include Claude Code, OpenAI Codex, Bazel and Chromium. A March 2026 test report says it is fully functional on Sequoia 15.x. Apple reportedly still uses the underlying Seatbelt for App Sandbox, with no replacement for ad-hoc CLI sandboxing. These are secondary sources. — [HN thread (simonw, 2025)](https://hn.svelte.dev/item/44283454); [gastown.dev: macOS sandbox-exec research, Mar 2026](https://gastown.dev/docs/research/macos-sandbox-exec); [Trail of Bits seatbelt-sandboxer](https://mintlify.com/trailofbits/skills/plugins/seatbelt-sandboxer); [codefly sandbox Go package](https://pkg.go.dev/github.com/codefly-dev/core@v0.2.28/runners/sandbox)
- **Windows (Codex CLI):** OpenAI's docs describe the Windows sandbox as experimental, launching commands with a restricted token derived from an AppContainer profile plus capability SIDs, and blocking network via proxy env overrides and stub executables. OpenAI's engineering post instead describes a write-restricted token (restricted SIDs: Everyone, logon session SID and a synthetic "sandbox-write" SID with write ACLs only on the workspace, `.git` denied). It says AppContainer was rejected because Codex "isn't a single, tightly scoped app". A secondary summary says firewall rules can't match synthetic SIDs, which forced a separate sandbox user plus an elevated one-time setup. — [OpenAI developers: Codex sandbox (search result)](https://developers.openai.com/codex/sandbox); [OpenAI: Building the Codex Windows sandbox (search result)](https://openai.com/index/building-codex-windows-sandbox/); [Daniel Vaughan deep dive, Jul 2026](https://codex.danielvaughan.com/2026/07/18/codex-cli-windows-sandbox-architecture-powershell-ast-safety-elevated-unelevated-appcontainer-restricted-tokens/)
- **Linux Landlock:** available since Linux 5.13 and lets unprivileged processes restrict themselves irreversibly. Filesystem rules came in ABI v1 (5.13), TCP bind/connect rules in ABI v4 (6.7), IOCTL filtering in ABI v5 (6.10). The `landlock` Rust crate offers best-effort compatibility with the running kernel. — [docs.rs landlock (search result)](https://docs.rs/landlock); [landrun Go package](https://pkg.go.dev/github.com/zouuup/landrun@v0.1.12); [Landlock + systemd talk, Sep 2025](https://landlock.io/talks/2025-09-30_landlock-systemd-asg.pdf)

### Inferences
- **Practical per-OS plan:**
  - Linux: keep systemd-run where available, and add Landlock as an in-process fallback for non-systemd and user-mode installs (aimx already has an `AIMX_SANDBOX_FORCE_FALLBACK` path).
  - macOS: run hooks via `sandbox-exec -p <profile>` with a generated Seatbelt profile, accepting the deprecation risk as Codex and Claude Code do.
  - Windows: v1 could use Job Objects (kill-on-close, CPU/memory limits) plus running hooks under the per-user daemon's own token, deferring real isolation. Codex's experience suggests a full Windows sandbox is a multi-month effort.
- App Sandbox (entitlement-based) is designed for `.app` bundles and Mac App Store apps, so it is not practical for arbitrary user-supplied hook argv (inference; not sourced).

### Gaps
- No primary Apple statement on sandbox-exec's current status or the macOS 26 "containers" feature as a replacement.
- No sourced comparison of bubblewrap vs Landlock, and no sourced detail on Windows Job Objects or AppContainer APIs (Microsoft docs blocked).

## 6. MCP integration: spec transports (2026), client configuration per OS, MCPB, MCP Registry, localhost HTTP security

### Takeaway
The current MCP revision is **2026-07-28**. It made the protocol stateless (no initialize handshake, no `Mcp-Session-Id`), removed the standalone GET SSE stream, and kept HTTP+SSE (2024-11-05) as deprecated. stdio remains the right default for aimx's `aimx mcp`: authorization for stdio comes "from the environment", and every major client supports launching a local command. One-click install for Claude Desktop is via an MCPB bundle (`server.type: "binary"` with per-platform overrides), which can also be listed in the official MCP Registry (still preview) as `registryType: "mcpb"`. If aimx adds a localhost Streamable HTTP endpoint, the spec requires Origin validation (403 on invalid Origin), recommends binding 127.0.0.1, and recommends authentication. CVE-2025-49596 (MCP Inspector, CVSS 9.6) shows what happens without it.

### Cited Findings

**Spec versions and transports**
- Spec version directories: 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25, **2026-07-28**, and draft. — [modelcontextprotocol GitHub: docs/specification](https://github.com/modelcontextprotocol/modelcontextprotocol/tree/main/docs/specification)
- The 2026-07-28 transports page defines two standard transports. **stdio** is newline-delimited JSON-RPC over a client-launched subprocess. **Streamable HTTP** POSTs each message to one endpoint, and the server replies with JSON or a request-scoped SSE stream. Custom transports over reliable byte streams (for example, Unix domain sockets) "SHOULD" reuse stdio framing. — [2026-07-28 transports/index.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/transports/index.mdx)
- Streamable HTTP (2026-07-28) has no protocol-level sessions (servers ignore `Mcp-Session-Id`). It requires the headers `MCP-Protocol-Version` (must match the body `_meta`, else 400 `HeaderMismatch`), `Mcp-Method`, `Mcp-Name` (for tools/call, resources/read and prompts/get) and `Mcp-Param-{Name}` for `x-mcp-header`-annotated params. GET and DELETE on the endpoint return 405. Change notifications come via a POST to `subscriptions/listen` (SSE response). No `Last-Event-ID` resumption. HTTP+SSE (2024-11-05) is deprecated, but servers may keep the old endpoints alongside, and clients fall back via POST then GET probing. — [2026-07-28 streamable-http.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx)
- Secondary coverage confirms the 2026-07-28 stateless change and says the SSE transport has an 18-month deprecation notice. — [Appwrite: MCP goes stateless in 2026-07-28](https://appwrite.io/blog/post/mcp-goes-stateless-in-the-2026-07-28-specification); [calmara: July 28 revision](https://calmara.app/blog/mcp-2026-07-28-spec-change)

**Security for localhost HTTP servers**
- Spec text (2026-07-28, "Security & Endpoint"): "Servers MUST validate the Origin header on all incoming connections to prevent DNS rebinding attacks." "If the Origin header is present and invalid, servers MUST respond with HTTP 403 Forbidden." "When running locally, servers SHOULD bind only to localhost (127.0.0.1) rather than all network interfaces (0.0.0.0)." "Servers SHOULD implement proper authentication for all connections." — [2026-07-28 streamable-http.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/transports/streamable-http.mdx)
- Authorization is OPTIONAL. HTTP transports SHOULD conform to the OAuth 2.1-based authorization spec (RFC 9728 Protected Resource Metadata, RFC 8707 resource indicators, client registration via Client ID Metadata Documents, pre-registration, or the now-deprecated Dynamic Client Registration). "Implementations using an STDIO transport SHOULD NOT follow this specification" and instead "retrieve credentials from the environment." — [2026-07-28 authorization/index.mdx](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/basic/authorization/index.mdx)
- CVE-2025-49596: MCP Inspector versions before 0.14.1 allowed remote code execution due to missing authentication between the Inspector client and its proxy (CWE-306, CVSS 9.6). Recorded Future describes exploitation from public web pages using the browser "0.0.0.0" quirk plus CSRF. — [NVD CVE-2025-49596](https://nvd.nist.gov/vuln/detail/CVE-2025-49596); [Recorded Future analysis](https://www.recordedfuture.com/blog/anthropic-mcp-inspector-cve-2025-49596); [GitLab advisory](https://advisories.gitlab.com/pkg/npm/@modelcontextprotocol/inspector/CVE-2025-49596/)

**MCP Bundles (.mcpb, formerly .dxt)**
- MCPB is a zip containing a local MCP server and `manifest.json` for one-click install. It was renamed from DXT (Desktop Extensions): the `dxt` CLI became `mcpb` and `.dxt` became `.mcpb`. Server types are Node (recommended, since Node ships with Claude for macOS and Windows), Python, UV and **binary** (static linking preferred). Binary bundles can ship Unix and Windows executables side by side. Claude for macOS and Windows is the named client. — [modelcontextprotocol/mcpb README](https://github.com/modelcontextprotocol/mcpb)
- Manifest spec v0.3 (updated 2025-12-02): `mcp_config` (command/args/env) with `platform_overrides` (win32/darwin). For binaries, "apps will automatically append `.exe` on Windows". `user_config` types are string (with `sensitive` for secure storage), number, boolean, directory and file. `compatibility` covers platforms (darwin/win32/linux) and a `claude_desktop` semver. Substitutions include `${__dirname}`, `${user_config.KEY}`, `${HOME}`. — [mcpb MANIFEST.md](https://github.com/modelcontextprotocol/mcpb/blob/main/MANIFEST.md)

**Official MCP Registry**
- The registry supports MCPB packages via `"registryType": "mcpb"` in `server.json`. The identifier URL must contain "mcp", and `fileSha256` is required (clients verify it before install). The registry is **still in preview**, and breaking changes or data resets are possible before GA. Examples use schema 2025-12-11. npm packages prove ownership via `mcpName` in package.json. — [MCP Registry: package types (search result)](https://modelcontextprotocol.io/registry/package-types); [Glama: server.json requirements, Jan 2026](https://glama.ai/blog/2026-01-24-official-mcp-registry-serverjson-requirements)

**Client configuration for local (stdio) servers**
- **Claude Desktop:** `claude_desktop_config.json` with a top-level `mcpServers` map (command, args, env). macOS path `~/Library/Application Support/Claude/`, Windows `%APPDATA%\Claude\`. Linux paths conflict between sources. Restart required. — [morphllm: Claude Desktop MCP](https://www.morphllm.com/claude-desktop-mcp); [inventivehq: config file locations](https://inventivehq.com/knowledge-base/claude/where-configuration-files-are-stored)
- **Claude Code:** `claude mcp add <name> -- <command> [args]` (stdio default) or `--transport http <url>`. Scopes: `local` (default, `~/.claude.json`), `project` (committable `.mcp.json`), `user` (`~/.claude.json`, all projects). Precedence: local > project > user. SSE still parses but is deprecated. (Secondary sources; one says it was checked against official docs Aug 2026.) — [computingforgeeks: Claude Code MCP setup](https://computingforgeeks.com/claude-code-mcp-servers-setup/); [Scrimba 2026](https://scrimba.com/articles/how-to-add-mcp-to-claude-code-2026/); [mcpbundles quick reference](https://mcpbundles.com/blog/claude-code-mcp-tools)
- **VS Code / Copilot:** `mcp.json` in the workspace (`.vscode/mcp.json`) or the user profile, with a top-level `servers` key. Stdio entries use `"type": "stdio"`, `command`, `args`, and an optional `inputs` array for secrets. `code --add-mcp '{"name":...,"command":...}'` is reported (single source). — [VS Code: MCP servers](https://code.visualstudio.com/docs/copilot/chat/mcp-servers); [VS Code: MCP configuration reference](https://code.visualstudio.com/docs/agents/reference/mcp-configuration); [Microsoft Learn: Visual Studio MCP servers (search result)](https://learn.microsoft.com/visualstudio/ide/mcp-servers)
- **Codex CLI:** `~/.codex/config.toml` or project `.codex/config.toml`, with an `[mcp_servers.<name>]` TOML table. `codex mcp login` stores OAuth tokens encrypted. **Gemini CLI:** `~/.gemini/settings.json` (or project `.gemini/settings.json`) `mcpServers`; remote uses `httpUrl`. **Cursor:** `~/.cursor/mcp.json` or `.cursor/mcp.json`; remote uses `url`. **Windsurf:** `~/.codeium/windsurf/mcp_config.json`; remote uses `serverUrl`. (Community guides.) — [inventivehq: add MCP server to AI coding CLIs](https://inventivehq.com/blog/add-mcp-server-to-ai-coding-cli); [squirrelscan: MCP clients](https://docs.squirrelscan.com/developers/mcp-clients); [openai/codex PR 4811](https://github.com/openai/codex/pull/4811/files)
- **Goose:** `~/.config/goose/config.yaml` (Windows: `%APPDATA%\Block\goose\config\config.yaml`) under `extensions:` with `type: stdio`, `cmd`, `args`, `enabled`, `timeout`. The env key name conflicts across sources (`envs` vs `env`). There is also a CLI `--with-extension 'ENV=val cmd args'`. — [Goose docs: config files](https://goose-docs.ai/docs/guides/config-files); [claudemarket: Goose MCP setup](https://claudemarket.ai/mcp/clients/goose); [goose-run man page](https://www.mankier.com/1/goose-run); [DeepWiki: Goose extension types](https://deepwiki.com/block/goose/5.3-extension-types-and-configuration)

### Inferences
- **Keep stdio `aimx mcp` as the primary integration.** It inherits the OS user identity, so the daemon's peer-credential authz works unchanged on Unix and via pipe token impersonation on Windows. This matches the spec's guidance that stdio credentials come from the environment, and it avoids the DNS-rebinding and OAuth surface entirely.
- **Per-client config writers:** aimx's existing `aimx agents setup` already embeds per-agent plugins. Extending it to write the MCP entry in each client's native format and path per OS (JSON `mcpServers` for Claude Desktop, Cursor and Gemini; `servers` + `type` for VS Code; TOML `mcp_servers` for Codex; YAML `extensions` for Goose; `claude mcp add` for Claude Code) is low-to-moderate effort. Field-name differences (`url` / `httpUrl` / `serverUrl`) matter only for HTTP.
- **MCPB:** a binary-type `.mcpb` containing per-OS `aimx` executables (darwin and win32 overrides) whose `mcp_config` runs `aimx mcp` gives Claude Desktop users one-click install. It only makes sense if the daemon is already installed, so the bundle is a client shim, not an installer for the daemon. Listing it in the MCP Registry (`registryType: "mcpb"`, sha256) is cheap, but the registry is preview.
- **Localhost Streamable HTTP:** worth adding only for clients that can't spawn processes (remote agent platforms, browser-based agents). If added: bind 127.0.0.1, validate Origin and Host, require a bearer token stored per-user (for example, in a 0600 file or the OS keychain via `keyring`), and implement the 2026-07-28 stateless headers. For truly remote access, OAuth 2.1 per the authorization spec is the compliant route but a large effort. Tailscale's CVE-2022-41924 (local TCP LocalAPI) and MCP Inspector's CVE-2025-49596 both argue for avoiding localhost TCP for privileged local control planes.

- modelcontextprotocol.io and the Anthropic/Claude docs domains were blocked, so client config details are mostly from community guides, not vendor docs.
- Did not verify which clients other than Claude Desktop support MCPB install (the MCPB README names only Claude for macOS/Windows), or whether Claude Desktop on Linux exists officially.
- Did not verify the rmcp crate's support status for the 2026-07-28 stateless Streamable HTTP revision.

## 7. Comparable Rust/Go tools that ship daemons cross-platform, and what they chose

### Takeaway
Successful cross-platform daemons converge on the same pattern: a native service manager per OS (systemd, launchd, Windows Service), a privileged local control channel that is not localhost TCP (UDS on Unix, ACL'd named pipe on Windows), and a separate per-user GUI or tray front-end on desktops. Mail-server peers (Stalwart) and sync tools (Syncthing) still lean on NSSM on Windows. Tailscale is the gold standard and also the most engineering-intensive.

### Cited Findings
- **Tailscale:**
  - macOS: Standalone GUI app (recommended), App Store app, or open-source CLI `tailscaled` as a launchd service. The GUI variants' daemons are "not technically tailscaled", and running two variants at once is discouraged. — [Tailscale macOS variants (search result)](https://tailscale.com/docs/concepts/macos-variants)
  - Windows: a service named "Tailscale". LocalAPI is on a named pipe in an admin-only namespace, with SDDL granting Users and SYSTEM, and caller identity from the impersonated token. — [Tailscale tailscaled (search result)](https://tailscale.com/docs/reference/tailscaled); [tailscale safesocket/pipe_windows.go](https://github.com/tailscale/tailscale/blob/main/safesocket/pipe_windows.go)
  - History: the earlier localhost-TCP LocalAPI on Windows led to CVE-2022-41924. — [INCIBE CVE-2022-41924](https://www.incibe.es/index.php/en/incibe-cert/early-warning/vulnerabilities/cve-2022-41924)
- **Ollama:**
  - Windows: per-user installer with no admin, a background tray app, and the API on localhost:11434. A standalone zip is offered for NSSM service use. — [Ollama windows.mdx](https://github.com/ollama/ollama/blob/main/docs/windows.mdx)
  - macOS: a drag-to-Applications menu-bar app that starts the server. Homebrew gives the CLI only, with a launchd service. — [lmsa.app 2026 guide (secondary)](https://lmsa.app/blog/how-to-install-and-configure-ollama-on-windows-and-mac-complete-2026-guide/)
- **Syncthing:** NSSM on Windows; a `~/Library/LaunchAgents` plist on macOS (or Homebrew); `syncthing@user` system unit or `syncthing.service` user unit on Linux. — [Syncthing autostart](https://docs.syncthing.net/users/autostart); [Syncthing autostart v1.0.0](https://docs.syncthing.net/v1.0.0/users/autostart); [Arch Wiki](https://wiki.archlinux.org/title/Syncthing)
- **Stalwart (Rust mail server, closest peer to aimx):**
  - Linux and macOS: one `sudo sh install.sh` writes a systemd, SysV or launchd unit.
  - Windows: manual NSSM or AlwaysUp. A forum report says the 0.16 Windows Server 2019 service fails on first start. — [Stalwart Linux/macOS](https://stalw.art/docs/install/platform/linux); [Stalwart Windows](https://stalw.art/docs/install/platform/windows); [Stalwart support forum](https://support.stalw.art/t/stalwart-on-windows-server-2019-fails-to-start-on-first-initialization/613)
- **ngrok agent:** `ngrok service install --config` gives a native Windows service (Event Log) and a launchd plist on macOS (syslog). It needs admin/sudo. — [ngrok: installing as a service](https://ngrok.com/docs/secure-tunnels/ngrok-agent/installing-as-a-service)
- **cloudflared:** `cloudflared service install` creates a LaunchDaemon as root or a LaunchAgent as a user; the default agent label is `com.cloudflare.cloudflared`. — [cloudflared mirror commit](https://git.nixnet.services/curben/cloudflared-mirror/commit/1b511b2d259db8e2c220313d34b74d443189b383)

### Inferences
- The closest template for aimx is a hybrid of ngrok and cloudflared (`aimx service install` that picks a system or user scope based on privilege) plus Tailscale (a named pipe with SDDL and token identity on Windows). Stalwart shows a mail server can ship on macOS via launchd with little extra work, and that Windows is where peer projects cut corners (NSSM).
- **Suggested phasing (inference):**
  1. macOS server and desktop via Homebrew formula plus `aimx setup` writing a LaunchDaemon (or LaunchAgent for user mode). Low effort: UDS and peer-cred authz carry over, and only hook sandboxing changes.
  2. Linux packaging (.deb/.rpm via cargo-deb and cargo-generate-rpm; user-mode systemd units with linger). Low effort.
  3. cargo-dist release pipeline with Homebrew tap, shell/PowerShell installers and Azure Artifact Signing. Low to moderate effort.
  4. Windows: service, named pipe and SID authz, per-user mode first. High effort.
  5. MCPB bundle and registry listing. Low effort once binaries exist.
  6. Optional localhost Streamable HTTP with token auth and Origin checks. Moderate effort.

### Gaps

- Did not verify how Tailscale's macOS Standalone variant registers its system extension or daemon (System Extension vs SMAppService).
- No sources found on how any of these projects handle running user-supplied hooks or scripts, which is aimx-specific.
